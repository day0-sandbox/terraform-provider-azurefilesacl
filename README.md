# terraform-provider-azurefilesacl

Terraform provider for managing Windows ACLs on Azure Files directories and files.

This provider is designed for Azure Virtual Desktop and FSLogix deployments that need Terraform-managed NTFS-style ACLs on Azure Files. It replaces ad hoc post-apply ACL scripts with a declarative resource:

```hcl
terraform {
  required_providers {
    azurefilesacl = {
      source  = "day0-sandbox/azurefilesacl"
      version = "~> 0.2"
    }
  }
}
```

```hcl
resource "azurefilesacl_file_acl" "profiles_root" {
  storage_account_resource_id = var.storage_account_resource_id
  share_name                  = var.share_name
  path                        = "/"
  resource_type               = "directory"

  mode                           = "additive"
  preserve_existing_unknown_aces = true
  identity_mode                  = "entra_kerberos_hybrid"

  access_control_entry {
    principal_id   = "SY"
    principal_type = "sid"
    rights         = "full_control"
    applies_to     = "this_folder_subfolders_files"
  }

  access_control_entry {
    principal_id   = "CO"
    principal_type = "sid"
    rights         = "modify"
    applies_to     = "subfolders_files_only"
  }

  access_control_entry {
    principal_id   = "user@example.com"
    principal_type = "user"
    rights         = "modify"
    applies_to     = "this_folder_only"
  }
}
```

Important: `azurerm_storage_share.acl` is a SAS stored access policy. It is not a Windows ACL. This provider manages the Azure Files security descriptor used for file and directory authorization.

## Provider Configuration

```hcl
provider "azurefilesacl" {
  tenant_id               = var.tenant_id
  auth_method             = "oauth"
  storage_endpoint_suffix = "core.windows.net"
  graph_endpoint          = "https://graph.microsoft.com"
  graph_api_version       = "beta"

  # Required only for auth_method = "account_key".
  account_key = var.account_key

  # Required only for auth_method = "sas".
  sas_token = var.sas_token
}
```

Supported authentication methods:

- `oauth`: Uses ambient Azure credentials through `DefaultAzureCredential`. The provider first attempts direct Azure Files bearer-token access. When that bearer-token path is unauthorized, the provider falls back to ARM `listKeys` plus shared-key Azure Files calls. This matches common Terraform operator permissions more closely than requiring privileged Azure Files backup roles.
- `account_key`: Uses a storage account key. Intended for local testing, prototype validation, or break-glass operation.
- `sas`: Uses a storage SAS token with the required Azure Files data-plane permissions.

`account_key` and `sas_token` are marked sensitive, but Terraform can still store sensitive values in state. Avoid committing state files.

## Resource

### `azurefilesacl_file_acl`

Manages the Windows ACL for one Azure Files directory or file.

Required arguments:

- `storage_account_resource_id`: ARM resource ID for the storage account. The provider derives the storage account name from this ID.
- `share_name`: Azure Files share name.
- `access_control_entry`: One or more managed ACE blocks.

Optional arguments:

- `path`: Directory or file path inside the share. Defaults to `/`.
- `resource_type`: `directory` or `file`. Defaults to `directory`.
- `mode`: `validate`, `additive`, or `authoritative`. Defaults to `additive`.
- `preserve_existing_unknown_aces`: Defaults to `true`.
- `owner_sid`: Owner SID or supported SDDL alias. Omit or set `preserve` to preserve the current owner.
- `group_sid`: Group SID or supported SDDL alias. Omit or set `preserve` to preserve the current group.
- `dacl_protected`: Whether generated authoritative DACLs are protected. Defaults to `true`.
- `identity_mode`: Required only when resolving `user` or `group` principals through Microsoft Graph.

Computed attributes:

- `id`
- `generated_sddl`
- `current_sddl_hash`
- `current_permission_key`
- `missing_managed_aces`

## ACL Modes

`validate` is read-only. It reads the live Azure Files ACL, resolves configured principals, and fails if any configured managed ACE is missing. It does not mutate Azure Files.

`additive` adds missing managed ACEs while preserving existing unknown ACEs, owner, group, SACL, and DACL flags. This is the default and the recommended mode for FSLogix root ACLs.

`authoritative` replaces the target DACL with the configured managed ACEs. It preserves owner, group, and SACL according to configuration. This mode requires explicit opt-in:

```hcl
mode                           = "authoritative"
preserve_existing_unknown_aces = false
```

## Delete Behavior

Destroy removes the exact ACEs generated by the resource from the live DACL, then removes Terraform state. Unknown ACEs, owner, group, SACL, and DACL flags are preserved.

Because matching is exact, if the same ACE existed before Terraform managed it, destroy cannot distinguish that pre-existing ACE from the managed one.

## Identity Resolution

Azure Files ACLs require Windows SID values in SDDL. The provider accepts direct SIDs, supported SDDL aliases, and Microsoft Graph principals.

### Direct SID or SDDL Alias

Use `principal_type = "sid"` for direct SID input. This path never calls Microsoft Graph and does not require `identity_mode`.

Supported aliases:

- `SY`
- `CO`
- `BA`
- `BU`
- `AU`
- `WD`

### Hybrid Identities

For these identity modes, Graph-resolved principals must expose `onPremisesSecurityIdentifier`:

- `ad_ds`
- `entra_domain_services`
- `entra_kerberos_hybrid`

Supported inputs:

- `principal_type = "user"` with user object ID or UPN.
- `principal_type = "group"` with group object ID.

### Cloud-Only Identities

For these identity modes, Graph-resolved principals must expose `securityIdentifier`:

- `entra_kerberos_cloud_only`
- `entra_kerberos_cloud_only_preview`

Supported inputs:

- `principal_type = "user"` with user object ID or UPN.
- `principal_type = "group"` with group object ID.

Display name lookup is not supported because it is ambiguous. UPN lookup is supported only for `principal_type = "user"`.

## Access Control Entries

```hcl
access_control_entry {
  principal_id   = "00000000-0000-0000-0000-000000000000"
  principal_type = "group"
  type           = "allow"
  rights         = "modify"
  applies_to     = "this_folder_only"
}
```

Fields:

- `principal_id`: SID, SDDL alias, Graph object ID, or user UPN.
- `principal_type`: `sid`, `user`, or `group`.
- `type`: `allow` or `deny`. Defaults to `allow`.
- `rights`: Named right or raw SDDL right. Mutually exclusive with `advanced_rights`.
- `advanced_rights`: List of advanced Windows rights that compose a numeric access mask.
- `applies_to`: Portal-style inheritance scope.
- `flags`: Raw SDDL ACE flags. Overrides `applies_to`.

Named rights:

- `full_control`
- `modify`
- `read_and_execute`
- `list_folder_contents`
- `read`
- `write`

Raw rights:

- `FA`
- `FR`
- `FW`
- `FRFX`
- Any hexadecimal mask such as `0x1301bf`

`applies_to` values:

- `this_folder_only`
- `this_folder_subfolders_files`
- `subfolders_files_only`
- `this_folder_subfolders`
- `this_folder_files`
- `subfolders_only`
- `files_only`

## Import

Import ID format:

```text
{storage_account_resource_id}|{share_name}|{resource_type}|{path}
```

Example:

```bash
terraform import azurefilesacl_file_acl.profiles_root "/subscriptions/00000000-0000-0000-0000-000000000000/resourceGroups/rg-avd-fslogix-hybrid/providers/Microsoft.Storage/storageAccounts/fsxavdfshybride64e1a|profiles|directory|/"
```

Import reads the target identity and sets the resource to `mode = "validate"`. It does not reverse-engineer arbitrary existing ACEs into Terraform configuration.

## Examples

The FSLogix root ACL example is in:

```text
examples/fslogix-root-acl
```

Run it locally with the provider development override:

```bash
cd examples/fslogix-root-acl
./test-local.sh validate
./test-local.sh plan
```

The helper builds the provider into `/tmp/azurefilesacl-dev` and sets `TF_CLI_CONFIG_FILE` to the example `dev.tfrc`.

## Known Limitations

The provider compares ACEs by exact SDDL string. Azure or Windows can normalize semantically equivalent ACLs differently, so future hardening should add deeper SDDL canonicalization.
